# Aztec Code (`breader-aztec`, milestone M10)

Design of the Aztec Code reader. Decoding (mode message, spiral extraction, Reed-Solomon, bit unstuffing, high-level modes) is implemented in `breader-aztec` ([as built](#as-built-decoding)); detection, sampling and the reader are not yet. Aztec is a 2D matrix symbology with a central bullseye finder and no quiet zone requirement. The reader works on the binary plane (`uses_binary() == true`) and handles inversion itself (`handles_inversion() == true`) through a polarity view like the QR `Plane`. Part of the cross-cutting [architecture](../ARCHITECTURE.md); status and read rates are in the [symbology index](README.md).

## Scope

- **In scope:** compact (1 to 4 layers) and full-range (1 to 32 layers) symbols, Aztec Runes (compact, 0 layers), all encodation modes (Upper, Lower, Mixed, Punct, Digit, Binary Shift), FLG(n) for FNC1 (GS1) and ECI, mirrored symbols, light-on-dark symbols.
- **Out of scope:** none planned.
- **Normative source:** ISO/IEC 24778.
- **Tests:** rxing's Aztec encoder (Apache-2.0) is a dev-dependency, to encode test symbols only. Clean-room: no decoder sources are read.

## Modules and data flow

`spec` (layer and codeword-size tables, mode-message layout, reference grid, spiral order), `build` (test and fuzz symbol writer on the same tables), `decode` (finder gate, mode message, codeword extraction, Reed-Solomon guard, bit unstuffing) with `decode/text` (high-level decoding) and `fuzzing`; still to come: `detect` (bullseye candidates), `sample` (core fit, orientation, layer sampling) and `reader`.

## Stages

1. **Bullseye candidates.** On rows of the binary plane, a run sequence of equal widths 1:1:1:1:1 around a dark center (compact: two dark rings around the center module; full-range: three) is a candidate center. Confirm on the column and both diagonals through the same center with the same module estimate (tolerance per run, like the QR finder ratio test), and count the rings on each ray to tell compact (bullseye 9×9 inside an 11×11 core) from full-range (13×13 inside 15×15). Candidates from several rows that agree are merged.
2. **Core fit.** Walk each ring boundary along rays from the center to get ring corners; fit a homography from the corners of the outermost bullseye ring (the square ring is preserved by perspective as a quadrilateral). Refine with the corners of the inner rings by least squares.
3. **Orientation and mode message.** The ring just outside the bullseye holds the mode message and the four orientation marks (3, 2, 1 and 0 dark modules at the four corners), which fix the rotation and detect mirroring (a mirrored symbol reads the marks in the other order). Read the mode message bits: compact 28 bits (7 four-bit words: layers − 1 in 2 bits, data codewords − 1 in 6 bits, 5 check words), full-range 40 bits (10 words: layers − 1 in 5 bits, data codewords − 1 in 11 bits, 6 check words). Reed-Solomon over GF(16) (x^4 + x + 1). Aztec Runes are compact symbols whose mode message (with the rune XOR pattern) is the payload.
4. **Layer sampling.** Layers wrap around the core two modules thick, spiralling outwards. Full-range symbols have a reference grid (alternating lines every 16 modules from the center); the grid points are located and used to re-anchor the mapping per block (piecewise homography), so large symbols survive perspective and slight warping. Modules under 3 px are sampled at their center, larger ones with a small majority vote. The total size follows from the layer count and is checked against the measured outer extent.
5. **Error correction.** Codeword size from the layer count: 6 bits (1–2 layers), 8 (3–8), 10 (9–22), 12 (23–32). Reed-Solomon over GF(64) (x^6 + x + 1), GF(256) (x^8 + x^5 + x^3 + x^2 + 1), GF(1024) (x^10 + x^3 + 1) and GF(4096) (x^12 + x^6 + x^5 + x^3 + 1), first root α^1. `breader-ecc` gets a generic binary-extension field with `u16` symbols for these (the existing `Gf256` stays as is). Misdecode guard, like Data Matrix: corrections are capped below the specification for small check counts (reserve 2 up to 7 check words, 1 up to 12; `2 * errors + erasures <= ec - reserve`) and data codewords of all zeros or all ones (invalid after bit stuffing; check codewords are not stuffed and may take any value) are erasures. The mode message RS is also capped (at most 1 correction for compact, 2 for full-range).
6. **Decoding.** Remove bit stuffing (a codeword of all ones but the last bit, or all zeros but the last bit, loses its last bit), then the high-level modes: Upper, Lower, Mixed, Punct, Digit with latches and shifts, Binary Shift (5-bit length, or 11-bit extended), FLG(0) = FNC1 (GS1 when first), FLG(1–6) = ECI with that many digits. Data outside an ECI is ISO/IEC 8859-1 (`Charset::Latin1`), as the standard's default interpretation.
7. **Results and metadata.** `SymbolMeta::Aztec(AztecMeta { compact, layers, data_codewords, ec_codewords, errors_corrected, erasures, mirrored, rune, eci })`. AIM identifier `]z` with the modifier described in [as built](#as-built-decoding). The quad is the symbol outline from the fitted mapping.

## Effort

Fast: row candidates every few rows, dark-on-light only (like Data Matrix). Balanced: all rows, both polarities, mirror retry. Exhaustive: also retries the core fit with each ring as the anchor and a grid-only resample.

## Evaluation

zxing-cpp `aztec-1` and `aztec-2` (48 labels) plus synth classes (compact and full-range, rotated, perspective, blur, low resolution, inverted, mirrored, runes). Targets: read at least as many as zxing-cpp, 0 false positives, no latency increase above 1 ms p50 Balanced on frames without Aztec (bullseye candidates must be cheap to reject).

## As built (decoding)

Input of `decode_grid`: the square module grid of the whole symbol (dark = true), rotated so that the orientation marks sit at the top-left (3 dark modules), top-right (2) and bottom-right (1) corners of the mode message ring, not mirrored. The detector will own rotation and mirror detection; `transpose` is the helper that turns a mirrored symbol into a regular one (the reflection across the main diagonal swaps the top-right and bottom-left marks), and the caller passes `mirrored = true` to record it. Everything below was checked against symbols encoded by rxing's encoder (compact 1 to 4 layers, full-range 1 to 32, all modes, ECI) and, for what that encoder cannot produce, against a symbol writer built on the same `spec` tables.

- **Symbol geometry.** Compact side `11 + 4 L`, full-range base `14 + 4 L` plus the reference grid: `base + 1 + 2 * ((base / 2 - 1) / 15)`, which gives 19 to 151. A compact and a full-range symbol can share a side (19, 23, 27), so up to two layouts are tried, the one whose finder scores better first. Data capacity `(88 + 16 L) L` bits compact, `(112 + 16 L) L` full-range; codeword size 6 (L up to 2), 8 (3 to 8), 10 (9 to 22), 12 (23 to 32); `total_bits mod word_size` modules at the start of the spiral belong to no codeword.
- **Finder gate** (before any error correction): at least 80 % of the bullseye modules (compact rings up to Chebyshev distance 4, full-range up to 6, even rings dark) and 10 of the 12 modules of the orientation corners must match.
- **Mode message.** Bits run clockwise from the top-left of the ring (compact: 4 sides of 7 modules at distance 5 from the center; full-range: 4 sides of 10 at distance 7, skipping the reference grid line through the center), four-bit words, most significant bit first. Compact: 2 bits layers − 1, 6 bits data codewords − 1, 5 check words; full-range: 5 bits, 11 bits, 6 check words; GF(16) with first root α¹. Corrections are capped by the same guard as data (at most 1 for compact, 2 for full-range). The layer count must give the grid side, and at least 3 check codewords must remain (the standard's minimum).
- **Data placement.** Layers from the outermost inwards, each in four sides (left going down, bottom going right, right going up, top going left) of pairs of modules across the two-module-wide layer, outer module first, on the lattice without the reference grid lines. The data codewords come first, so the spiral starts in the outermost layer; the check codewords end in the innermost.
- **Reed-Solomon.** `breader-ecc::Gf2m`: generator `(x − α¹)…(x − α^ec)`, highest-degree coefficient first, which matched rxing's encoder for all five fields without adjustment.
- **Bit unstuffing.** A data codeword whose first `w − 1` bits are equal has its last bit dropped (it is the complement); a data codeword of `w` equal bits is invalid and rejected if it survives correction. The end is padded with ones; the high-level decoder treats everything after the last zero bit as padding and rejects any other tail shorter than a code.
- **High-level tables.** Upper/Lower/Mixed/Punct/Digit as in the standard (5-bit codes, Digit 4-bit). A shift (P/S, U/S) takes one more code that must be a character or FLG; a latch, B/S or the Punct U/L code inside a shift is rejected. Binary Shift: 5-bit length, or 0 followed by 11 bits giving `length − 31`; it returns to the previous mode. FLG(n): FNC1 for n = 0; for 1 to 6, n digits of 4 bits each in Digit coding, whatever the current mode (rxing's encoder emits them that way); 7 is reserved and rejected. An ECI starts a new `DataSegment`; text outside any ECI is `Charset::Latin1`. A message with no data bytes is rejected.
- **FNC1.** The first FNC1 is dropped from the data and recorded: *first position* when no data byte precedes it, *second position* when exactly one letter or two digits precede it. Any other FNC1, and any later one, becomes ASCII 29 (GS).
- **AIM identifier** `]z` plus a modifier: `0` no FNC1 and no ECI, `1` FNC1 in first position (GS1), `2` FNC1 in second position (AIM), `3` ECI only, `4` ECI and first-position FNC1, `5` ECI and second-position FNC1; `]zC` for an Aztec Rune. Written from memory of the ISO/IEC 24778 / ISO/IEC 15424 option values, not verified against the text (see known gaps).
- **Aztec Runes.** An 11 × 11 grid (compact core only). The 28-bit mode message carries the 8-bit value as two words plus 5 check words, XORed with `1010…10` (28 bits, `0xAAAAAAA`); the rune value is also the payload as decimal text (`0` to `255`), `layers = 0`, `meta.rune = Some(value)`. The mask does not turn a Rune into a valid regular compact mode message within the correction cap (tested for all 256 values).
- **Metadata.** `AztecMeta` has no percentage of error correction (derivable from `data_codewords` and `ec_codewords`) and no structured append field, see below. `errors_corrected` includes mode message corrections; `erasures` counts erased data codewords that changed.
- **Fuzzing.** `fuzzing::{decode_grid, decode_bits, decode_stream}` back the `aztec_grid` target and `Gf2m` the `rs2m_decode` target ([fuzz](../../fuzz/README.md)).

## Known gaps

- Detection, sampling and the reader are not implemented.
- **Structured Append is not parsed.** The header (message ID between spaces, then two sequence letters) is part of the Upper-mode data stream and, as far as the standard text known to the authors goes, carries no flag of its own; parsing it would strip or reinterpret the first characters of ordinary messages such as `AB123`. The data is returned untouched and `AztecMeta` has no structured append field. To be settled against ISO/IEC 24778 before the reader ships.
- The Aztec Rune mask (`0xAAAAAAA`) and the `]z` modifiers are written from the standard as remembered; rxing's encoder cannot make Runes, so the rune path is only checked against our own writer. Re-check against the standard or a reference symbol.
- A P/S shift followed by the Punct U/L code, and other latch codes in a shift position, are rejected rather than interpreted.
